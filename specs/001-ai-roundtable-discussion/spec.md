# Feature Specification: AI Panel Studio — AI圆桌讨论核心功能

**Feature Branch**: `001-ai-roundtable-discussion`

**Created**: 2026-06-26

**Status**: Draft

**Input**: 构建「AI Panel Studio」AI圆桌讨论Web应用。首页展示讨论列表；嘉宾生成（LLM动态生成主持人+专家阵容）；演播厅实时讨论（主持人调度、专家自主发言、共识分歧实时更新）；多讨论并行隔离；SSE实时推送。

## Clarifications

### Session 2026-06-26

- Q: 讨论结束的主要触发机制是什么？ → A: 主持人判断 + 轮次上限兜底（主持人主导收尾，达到最大轮次时强制触发总结）
- Q: 讨论话题的内容审核策略？ → A: 后端集成第三方内容审核服务检查话题文本，不合规则拒绝创建并返回具体原因
- Q: SSE 断线重连后的数据恢复机制？ → A: 快照 + 增量补拉——重连时先返回当前状态快照（共识现状 + transcript 最后 N 条），再补发断线期间错过的增量事件
- Q: 并行讨论数达到上限时如何处理？ → A: 友好拒绝 + 引导——返回明确提示告知当前已满，引导用户等待某场讨论结束后再发起；首页显示当前讨论数/上限
- Q: 沉默专家（整场讨论未发言）如何处理？ → A: 标记但不阻断——专家状态标记为"沉默中"，讨论流程不受影响；讨论结束总结中注明某专家未发表观点

## User Scenarios & Testing

### User Story 1 — 发起新讨论：生成嘉宾阵容 (Priority: P1)

用户进入首页，点击"发起新讨论"，输入讨论话题（如"AI 是否应该开源？"）和期望专家人数（默认4人），系统调用大模型动态生成1名主持人 + 若干专家的角色阵容。每位嘉宾展示：姓名、职业/Title、立场简述、专属颜色标识。用户可确认阵容进入演播厅，或重新生成。

**Why this priority**: 嘉宾生成是整个讨论体验的入口——没有阵容就无法开始任何讨论。这是用户旅程的第一步。

**Independent Test**: 可通过"输入话题 → 查看生成阵容 → 确认/重新生成"完整闭环独立验证，无需后续演播厅功能。

**Acceptance Scenarios**:

1. **Given** 用户在首页, **When** 点击"发起新讨论"并输入话题"AI是否应该开源"、专家人数4, **Then** 系统生成1名主持人+4名专家，每位包含姓名、职业/Title、立场、专属颜色标识。
2. **Given** 用户看到生成的嘉宾阵容, **When** 某专家的立场与话题不相关或角色重复, **Then** 用户可点击"重新生成"获得全新阵容。
3. **Given** 用户满意嘉宾阵容, **When** 点击"确认阵容", **Then** 系统创建新讨论并导航至演播厅。
4. **Given** 用户未输入话题, **When** 点击"发起新讨论", **Then** 系统提示"请输入讨论话题"，不调用生成接口。
5. **Given** 用户输入专家人数为2, **When** 阵容生成, **Then** 系统生成1名主持人+2名专家，角色之间有足够观点多样性。

### User Story 2 — 首页讨论列表与加入观察 (Priority: P1)

首页展示所有进行中的讨论列表，每条显示讨论话题、主持人与专家人数、当前发言轮次、讨论开始时间。用户可点击任意进行中的讨论以观察者身份进入演播厅，也可发起新讨论。已结束的讨论标记为"已结束"并仍可查看回放。

**Why this priority**: 讨论列表是产品首页，所有用户的第一接触点。与P1-嘉宾生成并列构建MVP。

**Independent Test**: 可通过创建若干讨论后在列表中查看、点击加入来独立验证。不依赖演播厅完整功能——仅需讨论存在即可。

**Acceptance Scenarios**:

1. **Given** 系统中有3个进行中的讨论, **When** 用户访问首页, **Then** 看到3条讨论卡片，各显示话题、嘉宾人数、当前轮次、开始时间。
2. **Given** 用户在某讨论卡片上, **When** 点击"加入观察", **Then** 以只读身份进入该讨论的演播厅。
3. **Given** 某讨论已结束, **When** 在列表中显示, **Then** 标记为"已结束"状态，仍可点击查看完整transcript回放。
4. **Given** 没有进行中的讨论, **When** 用户访问首页, **Then** 显示空状态引导："还没有讨论，发起第一场吧"。

### User Story 3 — 演播厅实时讨论 (Priority: P1)

用户进入演播厅后：主持人自动进行开场白；专家根据当前讨论上下文自主决定发言（举手/抢答/补充/反驳），每次发言1–2句，禁止机械轮流发言。每位专家在独立状态小窗中显示当前状态（待发言/准备发言/发言中）及公开关注点。讨论 transcript 实时更新，每条发言显示发言人姓名+职业 Title+专属色块标识。讨论中持续提炼共识与分歧并实时推送更新。

**Why this priority**: 演播厅是产品核心体验——嘉宾自主发言、实时transcript、共识提炼全部在此发生。与P1列表、嘉宾生成共同构成MVP。

**Independent Test**: 在嘉宾阵容确认后，完整观看一场讨论：主持人开场→专家发言→transcript滚动→共识面板更新，可独立验证。

**Acceptance Scenarios**:

1. **Given** 讨论开始, **When** 主持人完成开场白, **Then** transcript 中显示主持人的开场发言，包含主持人姓名、职业 Title 和专属色块。
2. **Given** 主持人在发言中提出追问, **When** 某专家选择回应, **Then** 该专家自动获得发言权，发言1–2句后释放，不出现机械轮流。
3. **Given** 专家A正在发言, **When** 专家B有不同观点, **Then** 专家B可在下一轮获得发言权进行反驳，发言调度由系统根据上下文自主决定。
4. **Given** 每轮发言结束, **When** 系统提炼共识与分歧, **Then** 共识面板实时更新，显示当前已形成的共识点和存在的分歧点。
5. **Given** 某专家状态变化, **When** 专家从"待发言"变为"准备发言", **Then** 该专家状态小窗实时更新状态标签，但不暴露内部推理过程。
6. **Given** 讨论达到自然结束点, **When** 主持人进行总结, **Then** 总结为自然语言段落，不显示 JSON 或结构化数据。
7. **Given** transcript 中某条发言, **When** 显示在界面上, **Then** 仅显示发言人姓名+职业Title+发言内容+色块，不显示"举手""准备发言"等内部事件。

---

### User Story 4 — 多讨论并行与数据隔离 (Priority: P2)

系统支持同时进行多场讨论。每场讨论的状态、事件流、transcript、共识分歧数据以讨论唯一标识严格隔离。用户可以在不同浏览器标签页中同时观察多场讨论，互不干扰。

**Why this priority**: 多讨论并行是平台价值的关键——允许多个话题同时进行。但单讨论体验（P1）必须先稳定。

**Independent Test**: 同时创建2场不同话题的讨论，验证两场讨论的 transcript 和共识面板内容互不混淆。

**Acceptance Scenarios**:

1. **Given** 讨论A（话题"AI开源"）和讨论B（话题"远程办公"）同时进行, **When** 讨论A中专家发言, **Then** 讨论B的transcript中不出现讨论A的内容。
2. **Given** 用户同时打开讨论A和讨论B, **When** 讨论A结束, **Then** 讨论B不受影响继续运行，数据完全隔离。
3. **Given** 某讨论被删除, **When** 删除操作完成, **Then** 该讨论的所有关联数据（transcript、共识记录、嘉宾信息）被完全清除。

---

### Edge Cases

- 用户网络断开后重连：采用"快照+增量补拉"机制——先拉取当前共识现状+transcript最后20条，再补发断线期间错过的增量事件。3秒内恢复至最新状态。
- 专家人数设为1或设为10（边界值）：系统是否允许？生成的角色是否有足够多样性？
- 讨论话题为空或包含敏感内容：后端内容审核服务拦截并返回拒绝原因，前端展示具体提示（如"话题包含不当内容，请修改后重试"）。
- 并行讨论数量达上限：系统友好拒绝新请求，返回"当前讨论已满（N/N），请等待某场讨论结束后再发起"。首页实时显示讨论数/上限。
- 主持人生成失败（LLM 返回异常）：用户应看到友好错误提示并允许重试。
- 某专家连续多轮未发言：自动标记为"沉默中"状态，状态小窗同步更新。讨论结束时主持人总结中注明该专家未发表观点。沉默不影响讨论流程。

## Requirements

### Functional Requirements

- **FR-001**: 系统 MUST 在首页展示所有讨论列表，包含讨论话题、嘉宾人数、当前发言轮次、开始时间、状态（进行中/已结束）。
- **FR-002**: 系统 MUST 允许用户输入讨论话题与专家人数（默认4人、范围2–8人）。话题 MUST 经后端内容审核服务检查，不合规内容 MUST 拒绝创建并返回具体原因。通过审核后调用大模型生成1名主持人+N名专家的角色阵容。
- **FR-003**: 每位生成的嘉宾 MUST 包含：姓名、职业/Title、立场简述、专属颜色标识。阵容 MUST 保证角色间观点多样性。
- **FR-004**: 用户 MUST 可确认嘉宾阵容进入演播厅，或重新生成阵容。
- **FR-005**: 主持人 MUST 自动执行：开场白（引入话题、介绍嘉宾）、追问（针对专家观点深入提问）、串联（在专家发言之间过渡）、总结（自然语言段落，不显示JSON）。主持人每轮后评估是否应结束讨论并收尾；系统 MUST 设置最大发言轮次（默认30轮）作为兜底——达到上限时强制触发主持人总结。总结中 MUST 注明未发表观点的沉默专家。
- **FR-006**: 专家 MUST 根据当前 transcript 自主决定发言（举手/抢答/补充/反驳），每次发言1–2句。系统 MUST 禁止机械轮流发言模式。
- **FR-007**: 每位专家 MUST 拥有独立状态小窗，显示：当前状态（待发言/准备发言/发言中/沉默中）和公开关注点。MUST NOT 暴露隐藏推理过程（思维链）。连续多轮未发言的专家 MUST 自动标记为"沉默中"状态。
- **FR-008**: Transcript MUST 实时显示每条发言，包含：发言人姓名、职业/Title、发言内容，用专属色块区分发言人。MUST NOT 显示"举手""准备发言"等内部调度事件。
- **FR-009**: 系统 MUST 在讨论过程中持续提炼共识与分歧，并通过 SSE 实时推送到前端。共识与分歧 MUST 在讨论进行中不断更新，非讨论结束后一次性生成。
- **FR-010**: 系统 MUST 支持多场讨论同时进行（上限至少10场），以 discussion_id 严格隔离每场讨论的状态、事件流、transcript、共识与分歧数据。达到并行上限时 MUST 友好拒绝新创建请求，返回当前讨论数/上限与引导提示；首页 MUST 显示当前进行中的讨论数与上限。
- **FR-011**: 实时更新 MUST 通过 SSE（Server-Sent Events）实现。前端通过 SSE 连接接收 transcript 更新、嘉宾状态变化、共识分歧更新。断线重连时 MUST 采用"快照+增量补拉"机制：先返回当前状态快照（共识现状 + transcript 最后20条），再补发断线期间错过的增量事件。
- **FR-012**: 用户 MUST 可以观察者身份加入任意进行中的讨论，查看实时 transcript 和共识面板。
- **FR-013**: 已结束的讨论 MUST 保留完整 transcript 回放，用户可查看但不能交互。

### Key Entities

- **讨论 (Discussion)**: 唯一标识 discussion_id、话题 topic、状态（等待阵容/进行中/已结束）、创建时间、嘉宾阵容、当前轮次。
- **嘉宾 (Panelist)**: 所属讨论 discussion_id、角色类型（主持人/专家）、姓名、职业/Title、立场、专属颜色、当前状态（待发言/准备发言/发言中/沉默中）、公开关注点列表。
- **发言记录 (Transcript Entry)**: 所属讨论 discussion_id、发言人 panelist_id、发言内容、时间戳、发言类型（开场/追问/串联/陈述/补充/反驳/总结）。
- **共识记录 (Consensus)**: 所属讨论 discussion_id、共识内容、形成时间、涉及嘉宾列表、更新时间（实时增量更新）。
- **分歧记录 (Divergence)**: 所属讨论 discussion_id、分歧点描述、持方嘉宾分组、形成时间、更新时间。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 用户从输入话题到看到嘉宾阵容的平均等待时间不超过10秒。
- **SC-002**: 嘉宾阵容的角色多样性——在5次生成中，至少4次生成的专家之间立场有明显差异（不出现所有专家观点一致的情况）。
- **SC-003**: 在讨论进行中，每轮发言结束后共识/分歧面板在3秒内完成更新。
- **SC-004**: 系统支持至少10场讨论同时进行，各讨论数据完全隔离无交叉污染；达到上限时新请求被友好拒绝（返回提示，非静默失败）。
- **SC-005**: 用户在讨论过程中任意时刻刷新页面或断线重连后，能在3秒内通过快照+增量补拉恢复 transcript 和共识面板至最新状态，不丢失断线期间的发言和共识更新。
- **SC-006**: 90% 的用户在首次使用时能成功完成"发起新讨论→确认阵容→观看讨论"完整流程，无需帮助文档。
- **SC-007**: Transcript 显示的每条发言均正确标识发言人身份和色块，无色块混淆或发言归属错误。

## Assumptions

- 大模型 API 可用且响应稳定，单次生成请求在5秒内返回。
- 用户设备支持 SSE（所有现代浏览器均支持）。
- 专家人数范围设为2–8人（默认4人）是合理的——少于2人无法形成讨论，多于8人会导致界面拥挤和发言调度困难。
- 讨论结束由主持人每轮评估判断 + 系统最大发言轮次（默认30轮）兜底强制结束。轮次计数方式：每位专家一次发言计为1轮。
- 色块颜色从预设调色板中分配，确保相邻嘉宾颜色区分度足够。
- 观察者身份为只读——不能发言，也不影响讨论进程。
- 本阶段不涉及用户注册/登录系统，讨论为开放访问模式。
